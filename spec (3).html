🖥️ Screen Pop — What Staff Sees When a Call Comes In Powered by Managed365 caller ID match → HubSpot contact record · Internal staff view only
How it works: When an inbound call is received, Managed365 matches the caller ID to a HubSpot contact record. The screen pop surfaces key context before the call is answered. IVR selection is always first — staff sees either "Attendance" (IVR option 2) or "Front Office" (IVR option 3), which is the only call type signal available at MVP. All other context (parent name, campus, student, open tickets, last interaction) comes from the matched contact record. Fields marked ⚠️ TBD require a data decision before HIVE can configure.

📧 Email — How an Inbound Email Becomes a HubSpot Ticket Shared queue only · Personal inboxes not connected in MVP
When a parent emails a campus inbox (e.g. avondale-info@legacytraditional.org), the email routes into the HubSpot shared inbox for that campus. HubSpot attempts to match the sender's email address to an existing contact record. A ticket is auto-created and assigned per routing rules (paths E–H). Emails sent to a principal's personal Gmail are not captured in MVP — this is the friction point the journey map calls out. Staff must forward to the shared inbox, or a redirect rule must be configured.
✅ Matched
Sender email matches exactly one HubSpot contact record.
What happens:
→ Email logged to contact timeline
→ Ticket auto-created
→ Contact properties surfaced (name, campus, student, lifecycle stage)
→ Assigned per routing rules E–H
→ Staff sees full contact context when they open the ticket
No staff action required
⚠️ Multiple matches
Sender email matches more than one contact record (e.g. shared family email, duplicate records).
What happens:
→ HubSpot creates ticket but flags ambiguous match
→ Ticket assigned to front office queue unresolved
→ Staff must manually select the correct contact
→ Staff merges or corrects duplicate records
⚠️ Staff action required — select correct contact
🔴 No match
Sender email does not match any contact record. New parent, wrong email on file, or prospective family.
What happens:
→ Email lands in shared inbox as unassigned
→ Ticket created with no contact association
→ Staff must search by student name + campus
→ If found: manually associate contact to ticket
→ If not found: create new contact record, then associate
⚠️ Staff action required — search or create contact
No-match search protocol (training requirement)
Search by: (1) Student first + last name · (2) Parent name · (3) Campus filter. If no record found → create new contact with campus, name, and email → associate to the open ticket → note in Staff Notes that record was created at point of contact. Email match rate is a Day 1 dashboard metric — tracks data quality and drives the data cleanup backlog.

🚶 Walk-in (IRL) — How an In-Person Interaction Becomes a HubSpot Ticket Staff-initiated · No auto-trigger · Primarily a training requirement · Path L routing applies
Unlike phone (caller ID auto-match) and email (email address auto-match), walk-in interactions have no automatic trigger. Staff must open HubSpot and create the ticket manually during or immediately after the interaction. The identifier for a walk-in is student name + campus — staff searches by student to find the parent/guardian contact record. This makes walk-in the channel most dependent on training and adoption — every unlogged walk-in is an invisible interaction. Walk-in volume tracking is a Day 1 metric and adoption rate is the leading indicator of data quality for this channel.
Staff intake flow — step by step
1
Parent walks in — staff greets and opens HubSpot
Before engaging with the issue, staff opens HubSpot and searches for the contact. Search first — never create before searching.
2
Search by student name + campus
Primary identifier: student name. Secondary: parent name. Filter by campus to narrow results. This is the IRL equivalent of caller ID / email match.
3
Match found → open contact record · No match → create contact
If found: open contact, review open tickets and last interaction before engaging. If not found: create new contact (name, campus, phone if available) then proceed.
4
Create ticket — set contact reason and student info
Create ticket from contact record. Set Contact Reason immediately. Add Student Name + Grade Level. Channel = In Person (IRL). Priority and owner auto-set per Path L routing.
5
Handle the interaction — add staff notes
Log what was discussed, what was resolved or promised, any commitments made. Reference the HubSpot workbook for scripting on common issue types.
6
Close ticket — set resolution category and follow-up flag
Required at close: Resolution Category + Follow-up Required. If Follow-up Required = Yes and Contact Reason = Discipline or Withdrawal → auto-escalates to Admin queue (path O).
🔍 Walk-in — Contact Search States & Staff Protocol Student name + campus is the primary identifier · No auto-match possible
✅ Contact found
Student name + campus search returns one matching contact record.
What staff does:
→ Review open tickets + last interaction before engaging
→ Create ticket from contact record
→ Set Contact Reason + student info
→ Handle interaction, log notes
→ Close with resolution + follow-up flag
Standard flow — Path L
⚠️ Multiple results
Search returns more than one contact (common name, siblings, family with multiple students).
What staff does:
→ Confirm parent name and grade level verbally with the walk-in
→ Select the correct contact from the list
→ Proceed with standard flow
→ Note in Staff Notes if records appear duplicated
⚠️ Verbal confirmation required
🔴 Not found
No matching contact record. Prospective family, new enrollment, or data not yet in HubSpot.
What staff does:
→ Create new contact: parent name + campus + phone (if available)
→ Add student name + grade to ticket
→ Note "Created at walk-in" in Staff Notes
→ Handle interaction and close ticket normally
⚠️ Create contact first

⚠️ No call recording for walk-ins. Staff Notes is the only record of what was said during an IRL interaction. Unlike phone (call recording URL) and email (full email thread logged), walk-in has no automatic audit trail. Staff Notes quality is critical for escalation, follow-up, and repeat contact detection. This should be reinforced in training as the highest-stakes field for this channel.
📊
Walk-in adoption is a leading indicator of overall CRM adoption
Because IRL logging is 100% staff-initiated, the IRL volume trend in the first 30–60 days post-launch is the clearest signal of whether staff are consistently using HubSpot or reverting to sticky notes and memory. A flat or declining IRL volume line does not mean fewer walk-ins — it means staff are not logging. Campus leaders should review IRL volume weekly in the first quarter. Track: IRL Volume Over Time (report) + Staff Adoption rate (by campus).
